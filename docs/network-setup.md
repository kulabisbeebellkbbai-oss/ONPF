# Optional network deployment

Local launch binds `127.0.0.1:8765`. The URL works only on that computer; another device cannot use your loopback address. The supplied launchers never change firewall rules or deploy publicly. Use them for the default single-computer workflow.

Remote authenticated access is an explicit administrator deployment choice. Put Waitress behind an HTTPS reverse proxy, use a trusted certificate and an organization-approved DNS name, restrict network access appropriately, and keep the private instance/database outside public web directories. Run the service under a dedicated account with access only to its required files. A controlled reverse proxy can connect to loopback Waitress while users visit `https://programs.example.org`; a deliberate LAN-only binding uses that host's reachable address, not a remote client's `127.0.0.1`. Plain HTTP is suitable for local loopback testing, not remote authenticated use.

For the prepared AWS deployment, use the [AWS operator guide](aws-deployment.md) and [acceptance record](public-source-release.md). The production entrypoint is `/opt/onpf/current/.venv/bin/python -m onpf.production`; it requires the actual identified data mount, matching private marker, initialized database and canonical public hostname. Ordinary local CLI defaults remain unchanged. Startup does not initialize missing production storage.

The AWS configuration uses one trust path: Waitress trusts only the loopback Nginx peer and its overwritten `X-Forwarded-Proto`/`X-Forwarded-For`. Nginx fixes Host to the canonical name, scheme to HTTPS and client IP to its actual remote peer, discarding other forwarding authority. Do not add ProxyFix on top. Unknown Host/insecure scheme is refused; invitation URLs use canonical HTTPS. A different network deployment needs its own reviewed configuration and acceptance; the loopback CLI is not itself a remote HTTPS service.

Protect signing secrets and private backups, retain CSRF protection, and test login/logout, host rejection, secure cookies, invitation acceptance/revocation and upload limits through the actual proxy. Invitations and review links are bearer credentials: share them with intended recipients, use HTTPS, and revoke them when no longer needed. Batch closure also stops invitation submissions. New recovery instances rotate signing secrets and disable old invitations/review links, which must be generated again.

Local Windows tests cover loopback workflows and real Waitress production header/cookie boundaries. Real Nginx/TLS, mounted Linux storage, hardened services, AWS operations and sustained multi-user capacity have not been exercised here. The local launchers do not open network access. The AWS guide contains clearly labeled operator provisioning/DNS/certificate actions, which create resources only when deliberately executed with account authority.
