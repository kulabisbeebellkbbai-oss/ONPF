# Private backup, recovery, and recorded removal

Public ZIP exports contain editable approved program documents. They are **not backups**. Private JSON backups contain accounts (including password hashes), memberships, raw contributions and correction history, internal decisions, frozen approvals, shared-material provenance, and recorded removals. Restrict access to the installation administrator; encrypt stored/transferred backups and keep them outside publicly served directories. SHA-256 checksums detect corruption, not authenticity or permission to use a backup.

From the installation directory, use the project virtual environment:

```powershell
.venv/Scripts/python.exe -m onpf.cli --instance C:/private/onpf backup --database C:/private/onpf/onpf.sqlite3 C:/private/backups/PRIVATE-2026-09-26.json
.venv/Scripts/python.exe -m onpf.cli restore C:/private/backups/PRIVATE-2026-09-26.json C:/private/recovery/onpf.sqlite3
```

Both destinations must be new paths. Backup uses SQLite's consistent online snapshot, including committed WAL content. Restore accepts private format 1 with the exact historical application 0.1.0 migration prefix through `009_contact_log.sql` (including `007a_exports.sql`), the deployed Community Garden application 0.2.0 schema through `017_drafting_attempts.sql`, or the combined 0.2.0 schema through `018_ai_drafting.sql`. It validates original table/column sets, hashes, constraints, historical references, approvals and frozen schemas before migration. Unsupported or broken archives are rejected entirely. Restoration builds an unpublished database and publishes it atomically at a new path without overwriting another file. The running database is never opened or modified. Keep the old archive until a new combined backup and recovery rehearsal pass.

To rehearse recovery, restore into a separate private directory, then start the app against that database in a **new instance directory**. The CLI uses `<instance>/onpf.sqlite3` unless you supply `--database` after `serve`, `backup`, `redact-response`, or `create-user`. Always pass the same explicit database used by your launcher (`-DatabasePath` on Windows, the third script argument on Linux), demo, or recovered service. The CLI does not remember a running server's selected database. Keep `--instance` before the command and use the serving instance for removal so its configured export cache is cleaned. Backup reads the selected existing file without initializing an app; backup and removal refuse a missing source before creating an instance, secret or database. Account creation can initialize storage, so verify its chosen path. Each successful administrative command reports its selected source database.

For the restored custom path above:

```powershell
.venv/Scripts/python.exe -m onpf.cli --instance C:/private/recovery/new-instance serve --database C:/private/recovery/onpf.sqlite3 --port 8877
# In another terminal, administer that same storage:
.venv/Scripts/python.exe -m onpf.cli --instance C:/private/recovery/new-instance backup --database C:/private/recovery/onpf.sqlite3 C:/private/backups/PRIVATE-rehearsal.json
.venv/Scripts/python.exe -m onpf.cli --instance C:/private/recovery/new-instance create-user --database C:/private/recovery/onpf.sqlite3 --username new-facilitator
```

On Linux use `.venv/bin/python` with the same CLI option order. Verify account login, original/corrected response history, coverage, document drafts, frozen release hash and selected material notices before changing your production configuration. Retain the old installation until the rehearsal succeeds. Do not merge records from a backup into an active database.

Backups contain no live account sessions, login throttle state, AI drafting attempt counters or provider credentials, usable invitation/review-link hashes, signed browser receipts, or installation signing secret. Restoring resets AI usage counters; configure the provider separately using its protected credential file. Host snapshots and filesystem backups have their own scope and may include credentials. Invitation/review metadata remains for historical references, with disabled credentials and revoked status. Restored accounts keep their private password hashes and can log in again; create fresh invitations and review links. A fresh instance creates its own signing secret. Copying an old `.secret` file would defeat that rotation and is not part of recovery.

Recorded removal requires local administrative access and a persisted decision owner for the response's program:

```powershell
.venv/Scripts/python.exe -m onpf.cli --instance C:/private/onpf redact-response --database C:/private/onpf/onpf.sqlite3 RESPONSE-UUID --owner owner-username --reason privacy_request
```

Choose a nonpersonal reason code. `privacy_request` means participant privacy request; `retention_expired` means retention period expired; `captured_in_error` means capture error; `legal_requirement` means required removal under local policy or law. Free-text reasons are rejected so names, quotations, or details cannot be accidentally copied into a new audit record. The command records the owner, time, response ID, and chosen reason. There is no contributor-facing backup/restore/removal endpoint, and a different agency's owner cannot remove this program's input.

Removal clears original and all revision text, correction reasons, contributor label, quotation permission, response/revision entry-user references, related duplicate reasons, and disposition reasons. It discards the submission's arbitrary retry key and payload hash, including for multi-response submissions; other responses retain their capture data. IDs and links stay intact, preserving the fact that input existed and its place in decisions/coverage. The separate submission operator/invitation audit IDs remain nonpersonal identifiers; user accounts are not deleted by a response removal. Removed input cannot be reintroduced through correction. A fresh, authorized submission is a separate record.

Exact copied text is detected in draft question reasons, issued clarification round/question reasons and append-only deferral reasons, as well as across program drafts, proposals, decision/disposition text, review drafts, materials and versions, imported provenance, and candidate/release snapshots, including other programs in this local installation. Matching authored records are reported with IDs and content hashes, without copying the removed text into the report. The local administrator receives the complete report. The owner service result hides other agencies' record IDs and provides only a count. Review links containing detected copies are disabled. Known affected releases are withdrawn from future printing/export/reuse, configured cached ZIPs are deleted, affected immutable material versions cannot be adopted or reused, and matching mutable drafts require editing and new approval. Original immutable approved snapshots, approvals, hashes, and source terms are preserved as historical evidence; removal never makes old approvals appear to cover changed content. ID-only coverage/decision links do not themselves require withdrawal.

Copied editor content is **reported, not automatically erased**. Review each affected draft, proposal, decision, source/adaptation and downstream program; replace or appropriately restrict retained personal content and approve a new release. Original source notices and licenses must remain valid. Detection is best effort: partial quotations, paraphrases, spelling edits, and content introduced after removal may need manual review. Restricted historical evidence and imported provenance can still contain detected copies; a response removal is not a blanket purge of the whole installation.

Unavailable versions, including versions whose inherited terms contain known removed copies, are excluded from shared library previews and direct reuse. Private source drafts and historical releases remain behind program-scoped access. An affected current selection appears with nonpersonal identifiers and an unavailable status; its copied title, terms and content are hidden. Owners can adopt a clean version of the same material or use **Remove selection** if it is no longer needed. Repair several selections one at a time. Each replacement/removal checks the current program revision and changes the draft, requiring a new candidate and fresh approval while leaving old snapshots and approvals intact.

Creating another public review link checks the actual selected documents and program title for known copied text. Clean those fields or select clean documents before sharing. Unrelated private documents or decisions do not block a clean selected review. Previously revoked links stay revoked; a clean replacement needs its own new link.

For copied text in an append-only decision, record a clean replacement decision that explicitly **supersedes** the affected decision; do not edit or delete the old row. In each document that cites the retired decision, explicitly replace its supporting-decision selection with reviewed evidence or remove that support link, then save the document. Preparation returns an actionable conflict until those links are updated. Re-review the removed response's disposition, review the clean replacement documents, and prepare a fresh candidate for new owner approvals. New candidates omit only quarantined decisions that have been explicitly superseded; clean historical decisions remain evidence. Private history and older candidate/release snapshots keep the original records, IDs and approvals. The older affected release stays withdrawn, and restore checks each snapshot's own frozen supporting links rather than requiring historical evidence to match the current design.

Export generation, publication, and download payload capture serialize with removal. A newly withdrawn release cannot finish a new cached export after removal commits. Payloads dispatched before withdrawal and copies already downloaded, emailed, printed, imported elsewhere, or backed up cannot be recalled by this installation. Only the configured export directory is automatically cleaned; administrators must also handle alternate export locations and external copies.

Agree on a retention period and a named administrator before gathering actual input. Inventory private backups and copies, limit access, set deletion/expiry rules, and repeat recovery rehearsals. Older backups still contain earlier personal input and can reintroduce it on restore: remove expired backups or keep a separate removal register and reapply removal before making a recovered instance available. Database deletion removes accessible row values; SQLite free pages, journals, filesystem snapshots, and device-level recovery may retain storage remnants. For a sanitized database file, create a fresh logical backup after removal and restore it into a new private instance, then retire old files under your storage-retention policy. Do not claim secure media erasure or recall of external copies.


## Upgrade to 0.2.0 and rollback

Retain the trusted 0.1.0 release bundle and its independent checksum, and make a private pre-upgrade backup with that release before changing the running installation. Record the exact commit, archive checksum, frozen release IDs/content hashes and approvals. Stop writes during the production cutover. Rehearse on separate storage first: restore the old backup using 0.2.0, then verify corrected response history, issued batches, decisions, nonempty frozen releases and approvals. Opening an existing 0.1.0 database with 0.2.0 applies the packaged migration atomically; logical restore first verifies the supplied table/envelope checksums against the trusted old schema, validates its historical records, then migrates and validates current records before publishing new storage. Checksums establish integrity relative to the supplied envelope, not sender authenticity; retain an independently trusted backup checksum.

Rollback uses the retained 0.1.0 release and the pre-upgrade backup in new storage with a new instance/signing secret. Do not point the older application at the migrated database or remove migration rows/tables. Changes made after the backup are not in that rollback; retain the upgraded database privately for reconciliation and record the cutover boundary. Verify restored logins, revoked old links, historical release hashes and a new off-host backup before resuming service. This procedure documents local compatibility; production rollout and paid provider acceptance remain separate operator work.

Private 0.2.0 backups retain content-free AI origin manifests and private question/round/deferral metadata. They exclude raw generation prompts, rejected/unsaved output, signed browser receipts, runtime gateway credentials and signing secrets. Public editable packages remain format 1; private AI/context metadata is absent from public packages, release printouts, review links and invitation intake.

## Historical evidence and freshness limits

Restore checks strict manifest keys/types and hash syntax, referenced records, local program scope, response revision IDs, and surviving immutable evidence. Issued batch hashes admit their original open state or their recorded closure. Issued question hashes admit historical prefixes of append-only deferrals and the recorded removal exclusions. Decision hashes admit their original current state or the actual recorded successor. Shared material version bytes and inherited immutable terms are independently checked. Original signed-source manifests, issued context, frozen releases, content hashes and approvals are preserved; restore never repairs input hashes or requires old manifests to match current evidence.

Earlier mutable program/document/question/proposal/material contents and response classification states are not fully snapshotted. A syntactically valid historical hash cannot prove those missing bytes after an attacker recomputes an unsigned archive. Removed module selection and deleted shared-material adoption can also leave no historical authorization witness. A shared immutable material version with no surviving adoption witness is retained as historical provenance if its content and lineage validate; this does not prove its former program adoption. Restoring it grants no current selection, generation or save authority. Current evidence still requires current program authorization, safe content and an active adoption. Preserve the independently trusted original backup checksum to detect arbitrary envelope replacement.

Draft questions have a monotonic local context revision. Their fingerprints bind finite recorded/current direct-support descriptors; question references use intrinsic fields and local context revision, so self/cyclic references do not recurse. Direct support corrections, classifications and removals change current question evidence even if the aggregate program revision is unchanged. An accepted context refresh changes identity even when reason and handles stay the same. Unrelated aggregate-only revision touches do not change that direct support identity. Support text is not implicitly added to a question-only provider selection. This is a direct-support contract, not recursive freshness propagation through arbitrarily long question chains. Signed receipts remain strict and transaction-bound. Issued question/round contexts are immutable historical snapshots.

Removal quarantines matching private reason copies and records scope/content witnesses without deleting authored history. Clean a mutable draft reason explicitly; issue a later round or append later deferral history for subsequent work. Issued originals and earlier approvals remain private historical evidence. A clean release whose public content never contained the removed text remains usable.
