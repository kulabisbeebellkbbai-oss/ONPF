# Adopting and adapting programs

Download a public ZIP from an available approved release. It contains seven editable ODT and Markdown documents, a blank session template, budget CSV, framework/source JSON, notices, the MIT No Attribution (MIT-0) license and manifest checksums. Both the art and broader program have their own release/package. Public packages omit private raw responses, contributor identity, internal decision rationale, approvals/account data and credentials. Owners must still check authored document and material text for accidental personal information.

Unpack a ZIP to open its ODT documents in LibreOffice or another compatible editor, edit Markdown in a text editor and use the CSV in a spreadsheet. Keep the original package unchanged as your source record. SHA-256 checksums detect content corruption; they are not signatures, permission verification or proof of authorship. Importing accepts the supported self-contained format and verifies its declared members/hashes, schemas, source/version relations and retained terms. Do not substitute a private backup for a public program package.

Use Import public package in your authenticated workspace, choose the ZIP and supply your new local title. A successful import creates a new unapproved program with pending operating status and the importing account as its local owner. Foreign approvals and roles are not imported as local authority. Original public source content, hashes and notices remain provenance. Review all local documents, needs, staffing, accessibility, funding and operating permission before approval.

Imported shared materials become private local drafts retaining original terms; adoption is not automatic. In the material library inspect released versions and their permission basis/license/notices. An owner explicitly adopts a selected immutable version. Updating its source later leaves your selection unchanged. Compare versions using their readable content/permission differences and previews, then decide whether to adopt a newer version.

After recorded removal, affected shared versions and inherited terms disappear from library previews. Your existing selection remains visible as an unavailable marker with safe material/version references. Match its material reference to a clean replacement in the library, or choose **Remove selection** if you no longer need it. Owners can repair several selections sequentially; reload if another edit changes the program revision. Replacement/removal changes the current draft and needs a new candidate and fresh owner approvals. Old releases and approvals retain their original selections, including their withdrawal status.

To adapt a shared version, choose Create local adaptation. Edit the private draft's labeled fields and preserve its inherited notices and source terms. Releasing that draft and adopting it are separate owner choices. A local edit does not change the source agency's version. To offer an improvement, intentionally submit a note and optionally select sharing of the saved content snapshot. The source owner sees only that submitted proposal; no source update is automatic. Contribution back is encouraged, never required, and commercial/proprietary adaptations are permitted under MIT-0 for project-owned content; applicable third-party terms and inherited source notices still apply.

An art program can release its documents as a shared-material version; the broader program can adopt that exact version and release separately. Releasing new art documents does not change the broader release's frozen snapshot or selected version. This also applies after import/export and private restore. If a release is withdrawn after a privacy removal, stop distributing affected copies and follow the backup/removal guide; the local application cannot recall packages or paper already shared elsewhere.
